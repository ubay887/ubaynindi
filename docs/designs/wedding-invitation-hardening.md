## Problem Statement

Selesaikan dan kuatkan aplikasi undangan pernikahan pribadi agar tetap modern dan menarik, tetapi memiliki perilaku yang predictable, mudah dibaca, cepat di ponsel, dan tetap berguna pada perangkat atau browser lama. Perubahan sebelumnya sudah menyederhanakan generator tautan menjadi `?side=...&to=...`, menghapus autentikasi admin serta short code, mengganti musik, dan memperbaiki teks berbagi WhatsApp. Audit terakhir masih menemukan risiko deployment, guestbook lokal yang tidak benar-benar terkumpul, endpoint lama yang tidak lagi memberi nilai, beban awal yang terlalu besar, beberapa cacat UX, dan belum adanya regression test.

## What Makes This Cool

Undangan ini terasa seperti karya visual yang dibuat khusus untuk satu acara, bukan template generik. Pengalaman pembuka tetap memiliki karakter, tetapi informasi utama muncul cepat dan tidak bergantung pada animasi. Tamu dari ponsel baru maupun lama dapat membaca detail, membuka lokasi, mengirim RSVP/ucapan, dan membagikan undangan tanpa harus memahami mekanisme aplikasi.

## Constraints

- Digunakan untuk acara pribadi, bukan produk multi-tenant.
- Visual harus tetap modern, elegan, dan menarik.
- Keterbacaan, predictability, mobile-first, dan graceful degradation lebih penting daripada efek dekoratif.
- `/admin` tetap tanpa autentikasi dan hanya berfungsi sebagai generator tautan biasa.
- RSVP dan ucapan disimpan terpusat serta langsung dipublikasikan tanpa antrean moderasi.
- Deployment tetap memakai Next.js 16.3.0 standalone Docker di Coolify.
- Next.js 16 hanya menjamin browser modern; target realistis adalah pengalaman penuh pada browser yang didukung dan fallback informatif pada browser lebih lama, bukan janji identik pada “semua browser”.
- Data pribadi yang dikumpulkan dibatasi pada nama, status kehadiran, ucapan, dan waktu pengiriman. Alamat IP mentah tidak disimpan.

## Premises

1. Tampilan modern tidak identik dengan animasi panjang. Komposisi, tipografi, warna, fotografi, dan detail gerak singkat dapat mempertahankan karakter tanpa menunda konten.
2. `localStorage` tidak memenuhi kebutuhan “terkumpul dan terlihat banyak orang”; penyimpanan server-side yang durable diperlukan.
3. PostgreSQL di Coolify adalah pilihan paling sesuai karena deployment sudah berada di Coolify, submission dapat terjadi bersamaan, dan data tidak terikat pada lifecycle container aplikasi.
4. Publikasi otomatis tetap membutuhkan kontrol anti-abuse: validasi ketat, output escaping, honeypot, minimum submit time, rate limit terdistribusi, payload limit, dan prosedur penghapusan oleh pemilik.
5. Halaman generator tautan publik tidak boleh menjadi dashboard data sensitif. Penghapusan kiriman bermasalah dilakukan melalui runbook/database, bukan UI publik.
6. Realtime penuh tidak diperlukan. Kiriman baru langsung terlihat oleh pengirim setelah respons server; pengunjung lain melihatnya saat refresh atau polling ringan.
7. Static Open Graph images sudah cukup untuk WhatsApp dan lebih dapat diprediksi daripada endpoint OG dinamis per tamu.

## Research Basis

- W3C merekomendasikan target sentuh 44×44 CSS px untuk target penting dan mensyaratkan teks tetap berfungsi saat diperbesar 200%: https://www.w3.org/WAI/WCAG21/Understanding/target-size dan https://www.w3.org/WAI/WCAG21/Understanding/resize-text
- W3C menetapkan rasio kontras minimum 4.5:1 untuk teks biasa dan reflow tanpa scroll horizontal: https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html dan https://www.w3.org/WAI/WCAG21/Understanding/reflow
- web.dev menargetkan LCP ≤2.5 detik serta merekomendasikan early discovery dan prioritas tinggi untuk satu gambar LCP: https://web.dev/articles/optimize-lcp
- Dokumentasi lokal Next.js 16.3.0 menyatakan `Image priority` deprecated dan diganti `preload`; Route Handler bersifat uncached secara default; dukungan default dimulai dari Chrome/Edge/Firefox 111 dan Safari 16.4.

## Approaches Considered

### Approach A: SQLite pada volume persisten

Diff dan infrastruktur relatif kecil. Pendekatan ini cukup untuk satu instance, tetapi membutuhkan disiplin volume, backup file, locking, dan pembatasan agar Coolify tidak menjalankan lebih dari satu replica. Risiko operasionalnya lebih tinggi daripada manfaat penghematan setup.

### Approach B: PostgreSQL di Coolify

Gunakan service PostgreSQL terpisah, `DATABASE_URL` server-only, migration SQL yang versioned, dan Route Handler Next.js untuk membaca serta menulis guestbook. Pendekatan ini aman untuk concurrent writes, mudah di-backup, dan tetap sederhana untuk satu acara.

### Approach C: Hosted Supabase

Dashboard dan opsi realtime mempercepat operasi, tetapi menambah vendor, konfigurasi RLS, jaringan eksternal, dan surface area yang tidak dibutuhkan untuk proyek pribadi yang sudah dideploy lewat Coolify.

## Recommended Approach

Pilih Approach B: PostgreSQL di Coolify.

### Data model

Tabel `guestbook_entries`:

- `id`: UUID yang dibuat server.
- `guest_name`: 1–80 karakter setelah trim dan normalisasi whitespace.
- `attendance`: enum terbatas (`hadir`, `tidak_hadir`, `ragu`).
- `message`: 1–500 karakter.
- `created_at`: `timestamptz` dengan default waktu database.

Tabel `submission_limits`:

- key berupa HMAC harian dari client address yang sudah dipercaya dari reverse proxy, bukan raw IP.
- window, count, dan expiry untuk per-client serta global submission cap.
- cleanup expiry dijalankan saat write secara terbatas atau oleh maintenance command.

Tidak ada HTML tersimpan. UI merender string biasa melalui React dan tidak memakai `dangerouslySetInnerHTML`.

### Request flow

```text
Tamu membuka undangan
        |
        v
GET /api/guestbook?cursor=...&limit=20
        |
        v
PostgreSQL -> daftar terbaru + cursor berikutnya

Submit form
        |
        v
Origin + body-size + schema + honeypot + minimum-time checks
        |
        v
PostgreSQL-backed rate-limit transaction
        |
        v
INSERT guestbook_entries
        |
        v
201 + entry tersanitasi -> langsung muncul di daftar
```

### Ownership and deletion

- `/admin` tetap generator tautan publik dan tidak dapat membaca/menghapus guestbook.
- Sediakan maintenance script server-side untuk list/delete berdasarkan UUID dan runbook Coolify. Script membutuhkan `DATABASE_URL` dari environment server, sehingga tidak terekspos ke browser.
- Backup PostgreSQL harian selama masa undangan aktif. Tentukan tanggal retensi/penghapusan setelah acara.

### UI and compatibility

- Pertahankan identitas visual botanical-gold, tetapi tampilkan judul, nama pasangan, tanggal, dan tombol buka tanpa delay panjang.
- Batasi motion pembuka ke transisi singkat; hormati `prefers-reduced-motion`; semua konten tetap terbaca tanpa animasi.
- Gunakan semantic landmarks, focus states, kontras WCAG AA, tombol utama minimal 44×44 px, dan layout yang lolos pada 320 px serta zoom 200%.
- Sediakan fallback statis/noscript yang minimal menampilkan pasangan, tanggal, lokasi, dan kontak bila JavaScript gagal.
- Definisikan support matrix: full experience pada target Browserslist proyek; graceful fallback pada browser lebih tua. Uji Safari/WebKit, Chromium Android emulation, dan minimal satu perangkat Android lama nyata bila tersedia.

### Performance

- Ganti `priority` dengan `preload` pada satu gambar LCP yang benar dan pastikan URL-nya tersedia di HTML awal.
- Hilangkan animation delay 1.1 detik dari konten penting; target konten utama terlihat ≤300 ms setelah paint.
- Jangan preload bundle invitation-opened saat initial load. Warm up setelah first paint/idle atau saat intent (`pointerdown`/`touchstart`) dengan fallback aman.
- Lazy-load peta dan konten berat setelah dibutuhkan.
- Pertahankan audio `preload="none"`, kompres aset aktif, dan hapus MP3 lama yang tidak dipakai.
- Audit responsive `sizes`, format, kualitas, dan dimensi semua gambar.
- Target lab mobile: performance ≥90, LCP ≤2.5 s, TBT ≤150 ms, CLS ≤0.05, dan initial transfer ≤350 KiB tanpa audio.

### Deployment and cleanup

- Hapus seluruh referensi `DATA_DIR`, `data.seed`, dan `guests.json` dari Dockerfile, entrypoint, compose, environment example, dan dokumentasi.
- Jalankan migration sebagai langkah release/startup yang idempotent sebelum `node server.js`.
- Tambahkan health/readiness check yang membedakan aplikasi hidup dari database siap.
- Hapus `/api/og` dan rate limiter lama setelah memastikan tidak ada caller, karena metadata sudah memakai static OG images.
- Perbaiki dokumentasi agar standalone production dijalankan dengan `node server.js`, bukan `next start`.

### Test strategy

- Unit tests: parsing `side`/`to`, URL generator, teks WhatsApp, schema validation, pagination cursor, client-key normalization, rate-limit windows, dan migration helpers.
- API integration tests dengan database test: insert/list ordering, concurrent submit, invalid payload, honeypot, expiry, global cap, pagination, dan database outage.
- Playwright smoke tests: woman/pria link, guest personalization, open invitation, reduced motion, share fallback, map fallback, RSVP submit and refresh persistence, 320 px viewport, 200% zoom, admin generator, and absence of removed auth/short-code routes.
- Security checks: no raw IP persistence, no reflected/stored HTML execution, no unrestricted body, no secret in client bundle/log, trusted-proxy behavior, and dependency audit.
- Deployment verification: clean Docker build from Git checkout, migration against empty database, backup/restore drill, and Lighthouse rerun on invitation and admin.

## Open Questions

- Tanggal retensi guestbook setelah acara belum ditentukan. Default rencana: backup tetap disimpan 90 hari setelah acara, lalu diekspor dan database dapat dihapus.
- Daftar kata terlarang tidak dipakai pada versi awal karena dapat salah memblokir ucapan sah. Abuse ditangani dengan rate limit, honeypot, batas panjang, dan owner deletion runbook.
- Polling ringan untuk pengunjung lain ditetapkan 30–60 detik dan berhenti saat tab tersembunyi; tidak memakai WebSocket/SSE.

## Success Criteria

- Fresh Docker build dari Git checkout berhasil tanpa folder/file guest lama.
- RSVP/ucapan dari satu browser terlihat pada browser lain dan tetap ada setelah restart container.
- Submission normal langsung tampil; abuse controls menolak spam beruntun tanpa menyimpan raw IP.
- `/admin` dapat menghasilkan dan menyalin URL `?side=...&to=...` tanpa login serta tidak mengekspos data guestbook.
- Tidak ada request/caller ke endpoint auth, guest-code, guest JSON, atau dynamic OG lama.
- Invitation memenuhi target Lighthouse dan UX mobile yang ditentukan, tanpa horizontal overflow pada 320/390 px serta tetap usable pada zoom 200%.
- Jalur utama tetap menyediakan informasi acara ketika motion dimatikan, audio gagal, peta gagal, JavaScript terbatas, atau database sementara tidak tersedia.
- Lint, type/build, unit, integration, dan E2E smoke tests lulus; clean Docker build dan migration kosong terverifikasi.

## Distribution Plan

Existing Coolify deployment remains the delivery channel. The release adds a managed PostgreSQL service, server-only `DATABASE_URL`, idempotent migration before standalone server startup, health checks, and daily database backups. Deployment is staged first with an empty test database, then promoted after smoke tests and backup/restore verification.

## What I noticed about how you think

- You defined quality as “UI/UX predictable, keterbacaan clear, ringan dan mobile first,” which correctly puts the guest’s device and attention ahead of implementation novelty.
- You corrected the premise that usability should flatten the design: “tetap harus menarik, modern.” The plan therefore treats visual character and performance as simultaneous requirements.
- You chose immediate public visibility for RSVP and wishes. That favors social warmth, but it also makes bounded anti-abuse and an owner deletion path part of the feature rather than optional hardening.
